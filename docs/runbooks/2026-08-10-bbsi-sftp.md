# BBSI inbound SFTP — runbook

**Created:** 2026-08-10 · **Status:** account live but INERT (no key installed — nobody can authenticate)
**Purpose:** BBSI (PEO) delivers a recurring report to Splashworks over SFTP. Inbound only.

## Design decisions

| Decision | Choice | Why |
|---|---|---|
| Account model | **One org account `sftp-bbsi`, one public key per individual** | Individual credentials, individually revocable (delete one line). sshd logs the key fingerprint, so an upload is attributable to a person. One jail = one predictable destination for the report. |
| Direction | **Inbound only — no `extracts/` directory** | We publish nothing to BBSI. An empty `extracts/` reads as "a place to publish to" and invites a future script to do it. |
| Drop-off permissions | **`0700`** (Greenmill uses 0750) | All SFTP accounts share the `sftponly` primary group, so 0750 grants group-read to every other partner account. Chroot makes that unreachable over SFTP today — but a PII drop-off must not depend on a second control for its confidentiality. |
| Separation from Greenmill | **Separate user, separate jail, separate key file** | No shared path, no shared credential. Greenmill's jails were verified unchanged after creation. |
| Shared partner archive | **EXPLICITLY EXCLUDED** (`ARCHIVE_EXCLUDE=sftp-bbsi`) | Payroll/HR PII must not land in the general-purpose archive other tooling reads. Excluded by name, not by accident — BBSI sends no sidecar manifests today, so it would be skipped anyway; the day they send one it would silently start archiving PII to the wrong place. |

## What exists on prod (2.24.202.170)

```
/srv/sftp/sftp-bbsi/            root:root 0755   (chroot jail root)
└── incoming/                   sftp-bbsi:sftponly 0700   ← the only writable path
/etc/ssh/sftp-keys/sftp-bbsi    root:root 0644, 0 bytes   ← INERT until keys land
```

Account: system user, `/usr/sbin/nologin`, password locked (`passwd -S` → `L`), primary group `sftponly`.
Inherits the shared `Match Group sftponly` sshd block: chroot to `/srv/sftp/%u`, `internal-sftp -l INFO`
(per-file transfer logging), keys read from outside the jail, no password auth, no forwarding/tunnels.

Client sees exactly one directory: `/incoming/`.

## BBSI network details (Eric Whitchurch, BBSI IT — 2026-08-27)

- **BBSI egress IPs: `96.95.77.209` and `32.132.45.26`.** Their firewall is open to us.
- Every key line MUST carry `from="96.95.77.209,32.132.45.26"` — a leaked private key is then
  unusable from anywhere but BBSI's network. Closes the source-IP half of IN-17 for this account.
- **Watch item:** Eric asked "who needs an SFTP client installed on their computer," which implies
  manual uploads from individual workstations and, with "install the private key in the SFTP client,"
  possibly ONE private key copied to several laptops. **Ask for one key PER PERSON.** A shared key is
  neither revocable per person nor attributable. If the report is generated on a schedule it should
  upload from a server with a single service key, not from anyone's laptop.

**Terminology note** — Eric's email reads ambiguously: "share the public key with the client" means
share it with *Splashworks*; "install the private key in the SFTP client" means the *software*. Two
senses of "client" in one sentence. His flow is correct: BBSI keeps the private key, sends us the
public half only.

**What the keypair does and does not do:** it authenticates *who is connecting*. It does NOT encrypt
the session — SSH negotiates that separately via ephemeral Diffie-Hellman, so the channel is encrypted
even under password auth. SFTP therefore gives confidentiality IN FLIGHT ONLY; the file lands as
plaintext on our disk. Encryption at rest remains open (OPEN item 5).

## Activation — when BBSI sends their public key(s)

1. Collect one **public** key per individual (`ssh-ed25519` preferred; never accept a private key).
2. Append to `/etc/ssh/sftp-keys/sftp-bbsi`, **one line per person, `from=`-restricted, comment = their email**:
   ```
   from="96.95.77.209,32.132.45.26" ssh-ed25519 AAAA...  jane.doe@bbsi.com
   from="96.95.77.209,32.132.45.26" ssh-ed25519 AAAA...  bob.smith@bbsi.com
   ```
   The file is pre-staged on prod with this guidance inline; paste real keys beneath it.
3. Verify: `ls -l /etc/ssh/sftp-keys/sftp-bbsi` → `root:root 0644`. No reload needed (`AuthorizedKeysFile` is read per-connection).
4. Have them test: `sftp -i <key> sftp-bbsi@2.24.202.170` → `put testfile` into `/incoming/` → confirm the Slack #alerts login+upload notification fires.

**Connection details to give BBSI:** host `2.24.202.170`, port `22`, user `sftp-bbsi`, key auth only, upload path `/incoming/`.

## Offboarding an individual
Delete their line from `/etc/ssh/sftp-keys/sftp-bbsi`. Effective on next connection; no other change.

## What is already wired automatically
- **Slack #alerts** — `notify-sftp-access.sh` matches `sftp-*`, so BBSI logins and uploads alert with no change.
- **Transfer logging** — `internal-sftp -l INFO` records every open/close with filename and byte count.
- **Nightly report** — `report.py` globs `/srv/sftp/*/incoming`, so BBSI files appear in the ingestion email. They will show as **unverified** (BBSI sends no checksum sidecar) — that is honest, not a fault.

## Direction: CONFIRMED PUSH (Ross, 2026-08-28)

BBSI uploads to us; we do not pull from them. Reasoning, so it is not re-litigated:
- **Credential asymmetry runs the right way.** We hold nothing of BBSI's — they keep their private
  key, we hold a public key that is worthless if stolen. A pull model would put a live credential to a
  payroll provider on our disk.
- **Blast radius points outward.** A BBSI compromise can write into a chrooted 0700 dir that nothing
  ingests automatically. Our compromise, under pull, would reach into BBSI.
- **Their change control is the long pole** and is already done for push (firewall policy + keys).
- **We keep the authoritative transfer log** (`internal-sftp -l INFO`) rather than asking them for it
  during an investigation.

**The cost of push, stated plainly: absence is ambiguous.** No file on a given day is
indistinguishable between "they didn't run it", "their job failed", "they uploaded elsewhere", and
"the report was empty". Silence reads exactly like success. Mitigation is an **expected-arrival
check** — register the feed with a cadence + tolerance and alert on the gap (the ETL-10 /
`feed_registry` pattern). This CANNOT be built until BBSI commits to a schedule.

## OPEN — decisions required before anything consumes this data

1. **Custody.** BBSI files currently live only in the partner-writable jail. That is not a backup (see `feedback_writable_location_is_not_a_backup`). A restricted archive path with its own retention clock is needed — destination, retention period, and who may read it are Ross's calls.
2. **Filenames in email.** The nightly report lists drop-off filenames. Harmless for `BBSI_Payroll_Register_20260810.csv`; a leak if BBSI names files per-employee. Check a real sample before the first report goes out; suppress filenames for this source if needed.
3. **Integrity.** No checksum/manifest convention agreed with BBSI. Worth asking — it is what makes a truncated upload detectable.
4. **Retention/disposal.** PII needs a defined lifetime in the jail. The existing audit-retention pattern (redact @90d, delete @365d) is a starting reference.
5. **Encryption at rest** — unresolved; the VPS disk is not encrypted at rest.
6. **Arrival monitoring — blocked on BBSI.** Need a committed cadence (time + days), a predictable
   dated filename convention, and ideally a checksum/manifest sidecar (same shape Greenmill sends;
   without one a truncated upload is undetectable). Until the cadence is known, a missed delivery is
   invisible.
7. **Ingestion.** Nothing reads these files. Whether this data ever enters the warehouse — and under what access controls — is a separate decision, not implied by delivery.
